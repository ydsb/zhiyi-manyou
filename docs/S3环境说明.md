# S3 开发环境说明（Python 侧）

> 记录本机把 Python 生态跑起来的过程与踩到的坑。换机器或重建环境时按本文操作。

## 一、本机的三个限制（决定了整套方案）

| 限制 | 表现 | 影响 |
|---|---|---|
| **Python 的 TLS 被拦** | `pip` / `python -m venv` 联网报 `SSL: UNEXPECTED_EOF_WHILE_READING` | 常规方式装不了任何包 |
| **临时目录有文件锁** | pip 解包时报 `[WinError 5] 拒绝访问`（拒绝访问它自己刚写的临时文件） | 即使下载成功也装不上 |
| **无 Docker** | 无法用容器起 Elasticsearch | 向量检索需换实现 |

关键观察：**JVM 自带的 TLS 栈不受影响** —— 实测 Java 能正常访问 PyPI、Maven Central
与国内镜像，而 PowerShell / git / python 都失败。因此整套方案围绕"用 Java 做网络通道"构建。

## 二、工具链（三个脚本 + 一个代理）

```

└── python-venv\              安装目标（Lib\site-packages）
```

### 1. 启动镜像代理（必须先做）

```powershell
java G:\DEV\_tools\PyMirror.java --port 8899 --cache G:\DEV\pypi-cache
```

它做三件事：
- `GET /simple/<包名>/` → 从上游镜像取索引页，**把下载链接改写为经本服务中转**；
- `GET /file/<文件名>?u=<上游URL>` → 回传 wheel；
- 上游主机白名单校验，不代理任意地址（避免变成开放转发器）。

**踩坑记录**：最初把上游 URL 整个编码进查询串、路径固定为 `/file`，
结果 pip 报 `No matching distribution found`。原因是 **pip 要从 URL 路径末段解析
wheel 文件名**，据此判断包名、版本与 Python 标签（`cp313-win_amd64`）。
修正为 `/file/<文件名>?u=<上游URL>` 后即可正常工作。

### 2. 解析依赖并安装

```powershell
# 自检（确认代理可用）
python G:\DEV\pytools\pydep.py check

# 只看依赖树
python G:\DEV\pytools\pydep.py resolve fastapi uvicorn

# 解析 + 下载 + 安装
python G:\DEV\pytools\pydep.py install numpy fastapi uvicorn
```

`pydep.py` 的工作方式：
1. 从代理索引页挑出与当前环境兼容的 wheel（`cp313` + `win_amd64`，纯 Python 包优先）；
2. 下载 wheel 到 `G:\DEV\wheels`；
3. **在内存里读 zip 中的 `METADATA`** 解析 `Requires-Dist`，递归解析传递依赖；
4. **自行解包安装**到目标目录（不经 pip，因为 pip 必然经过临时目录而失败）；
5. 安装前清理同包旧版本目录与 `dist-info`。

### 3. 使用已安装的包

包装在非标准位置，需要设置 `PYTHONPATH`：

```powershell
$env:PYTHONPATH = 'G:\DEV\python-venv\Lib\site-packages'
python your_script.py
```

或用该 venv 的解释器（同样需要 `PYTHONPATH`，因为没走 `ensurepip`）：

```powershell
& 'G:\DEV\python-venv\Scripts\python.exe' your_script.py
```

## 四、pydep.py 开发中修掉的三个缺陷

这三个都是**真实踩到的**，记录下来避免重犯：

1. **`fileNameOf` 没剥查询串** → `endsWith(".whl")` 永远为 false，一个文件都匹配不到。
   走本地代理时链接形如 `/file/xxx.whl?u=https%3A...`，必须先把 `?` 之后截掉。
2. **预发布版被当成正式版** → 解析出 `pydantic 2.14.0b2`、`typing-extensions 4.16.0rc2`。
   排序需先按"是否预发布"分组，稳定版优先（与 pip 的默认行为一致）。
3. **同包多版本时靠字典覆盖随机选中** → 安装环节原本扫描 wheel 目录建 `包名 → 文件` 映射，
   目录里同时有 `pydantic-2.13.5` 与 `pydantic-2.14.0b2` 时，字面排序让后者胜出，
   于是稳定版解析结果被预发布版覆盖。修正为**显式传递解析出的 wheel 文件名**，不再靠目录扫描。

## 六、NLP 语义引擎的实际实现（S3 核心产出）

在"装不了预训练模型、起不了 ES"的约束下，用**纯算法 + numpy** 实现了完整的
语义匹配链路，接口与预训练方案保持一致，日后替换只需改实现类。

### 代码结构

```
nlp-service/
├── nlp/
│   ├── tokenizer.py    中文分词与 n-gram（技能短文本专用，无需词典）
│   ├── tfidf.py        TF-IDF 向量化（IDF 由技能语料预先拟合）
│   ├── corpus.py       训练语料加载（技能 + 需求 + 图谱关系）
│   ├── embedder.py     潜在语义分析：随机化截断 SVD → 稠密向量
│   └── index.py        向量索引与检索（精确 KNN / 可选 LSH / 图谱加成）
├── train.py            训练脚本（读库 → 拟合 → 建索引 → 自检）
├── serve.py            FastAPI 算法服务（供 Java 调用）
├── tests/test_nlp.py   44 项单元测试
└── models/             训练产物（可复现）
```

### 与需求约定的对应关系

| 需求约定 | 本项目实现 | 说明 |
|---|---|---|
| `sentence-transformers` 预训练模型 | TF-IDF + 随机化截断 SVD（LSA） | 装不了 torch、访问不了 HuggingFace |
| Elasticsearch `dense_vector` + HNSW | numpy 精确余弦检索 + 可选 LSH 预筛 | 无 Docker；千级规模下精确检索更快更准 |
| FR-M3-02 ANN | 默认精确 KNN，`mode=lsh` 可切换 | 统一走 `VectorIndex.search()`，上层无感 |
| FR-M3-05 可解释理由 | 每个命中带 `reasons` | 含共有语义片段与图谱加成说明 |
| NFR-R-03 降级通道 | `SemanticMatchClient` 熔断 + 降级 | 算法服务挂了自动走关键词，业务不中断 |

### 实测性能与效果

| 指标 | 数值 |
|---|---|
| 语义检索耗时 | **11 ms**（NFR-P-01 要求 P95 ≤ 300ms） |
| 索引规模 | 27 条（14 技能 + 13 需求），维度 26 |
| 跨表述匹配 | 「需要做数据大屏要有图表」→ ECharts 数据可视化 **0.5908** |
| 图谱加成 | 「需要有人帮我做界面设计」→ UI/UX 设计 **0.7999**（+0.30 同义关系） |
| 相似度判定 | 「想学数据可视化做毕设图表」↔「ECharts 数据可视化」**0.9912** |

### 开发中确立的两个重要结论

**1. 图谱关系不能拼进训练语料，只能在检索阶段加成。**

最初把图谱边拼成训练样本（"A B 互补"）期望 SVD 拉近两者。实测相反：
在 20 篇语料、16/32/64 三种维度下，相似度一致地**下降**（0.0545 → 0.0295）。
根因是 IDF 机制 —— 拼接文档使共享词的文档频率升高、IDF 降低，
归一化后共享特征权重反被压低。**这是 IDF 的必然结果，调参无法解决。**

改为检索阶段的显式加成后：关系不混进向量，而是一次可控、可解释、可关闭的加权，
用户能看到"因为图谱标注二者互补所以提权"。

**2. LSA 无法凭空建立联系 —— 多路召回是必需的，不是可选项。**

若两段文本完全不共享 token、语料又小，其向量会落在**正交**方向上（余弦为 0），
此时注入图谱关系也难以拉近。这意味着：

- 向量召回擅长"泛化"（没见过的新表述也能匹配到相近的）；
- 图谱召回擅长"精确"（专家标注的确定关系，哪怕文本毫无重叠）；
- **两者必须并联**（FR-M3-04 多路召回），不能指望向量独自覆盖所有跨域关系。

这一条已用单元测试固定（`test_lsa_orthogonal_boundary`），
防止日后有人误以为语义匹配可以替代图谱。
