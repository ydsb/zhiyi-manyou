## 1. 引言

### 1.1 编写目的
本文档定义"知驿·漫游"平台的功能需求、非功能需求、数据需求与验收标准，作为开发、测试、结项验收的统一依据。读者对象：项目团队成员、指导教师、学院及省教育厅评审专家。

### 1.2 项目背景
跨学科学习已成为数字时代人才培养的核心诉求，但校园内存在三重障碍：
- **信息障碍**：技能供需分散在 BBS、QQ 群、朋友圈，靠"人工喊话"撮合，效率极低；
- **语义障碍**：不同专业术语体系割裂，艺术设计专业的"动态交互效果"与计算机专业的"Vue 响应式 / JS 动画库"描述同一需求却互相搜不到；
- **信任障碍**：陌生同学之间进行深度技能交换时，缺乏履约凭证与评价公信力，试错成本高。

现有工具（校园论坛、群聊、通用社交软件）只能完成"信息发布"，无法覆盖 **匹配 → 协作 → 记录 → 评价 → 能力沉淀** 的全链条，导致非正式学习成果无法被认定，学生跨学科投入缺乏正反馈。

### 1.3 项目目标
构建一个 **去货币化"以技易技"** 的校园跨学科技能交换与学习记录平台，实现：

| 编号 | 目标 | 可量化指标 |
|---|---|---|
| G1 | 打破学科语义壁垒，实现技能供需的语义级智能匹配 | 跨专业术语匹配准确率 ≥ 70%（人工标注测试集） |
| G2 | 全过程记录学习轨迹，把隐性能力转化为可视化数字凭证 | 覆盖 100% 已完成交换的协作行为留痕 |
| G3 | 建立不可篡改的过程性评价与信用体系 | 评价记录哈希固化率 100%，可校验 |
| G4 | 沉淀跨学科技能知识资产 | 知识图谱覆盖 ≥ 50 个二级学科、≥ 1000 个核心技能标签 |
| G5 | 完成可示范的校园落地验证 | ≥ 3 个不同学科背景学院闭环试运行 |

### 1.4 术语与缩略语
| 术语 | 说明 |
|---|---|
| 技能驿站（驿） | 平台中一个可被交换的技能单元 / 服务节点 |
| 漫游 | 用户跨学科、跨院系的技能探索与交换行为 |
| 以技易技 | 平台核心交易逻辑：不使用货币结算，以技能换技能 |
| 技能星图 | 新用户首次登录后由所选标签实时渲染的初始技能可视化图 |

| 能力雷达图 | 多学科维度的能力可视化图表 |
| 数字勋章 | 基于协作成果授予的数字化凭证（像素艺术 / 体素化风格） |

## 2. 总体描述

### 2.1 产品定位
**面向高校"第二课堂"与终身学习的轻量化、可示范一体化解决方案**。区别于通用社交平台与在线课程平台（MOOC）：本平台不做内容售卖、不做货币结算，而是把"人与人之间的技能互补关系"作为核心资源进行语义匹配与可信记录。

### 2.2 用户角色

| 角色 | 描述 | 主要权限 |
|---|---|---|
| 游客 | 未登录访客 | 浏览公开技能卡片、平台介绍、排行榜（脱敏） |
| 普通用户（学生） | 平台主体用户，经统一身份认证登录 | 发布供需、语义检索、发起/接受交换、协作打卡、双向互评、查看个人数字档案、申诉 |
| 仲裁委员 | 由高信用、跨学科核心用户担任 | 查看争议卷宗、匿名投票裁决 |
| 平台管理员 | 运营与运维人员 | 用户管理、标签与知识图谱维护、内容审核、异常订单干预、数据统计 |
| 算法服务（系统角色） | 匹配与推荐引擎 | 读取画像与技能向量、写入推荐结果（无用户隐私原文访问权） |

### 2.3 运行环境
| 层次 | 要求 |
|---|---|
| 终端 | PC 浏览器（Chrome / Edge 现代版本）、移动端响应式适配（≥ 375px 宽） |
| 浏览器 | 支持 ES2020，无需 IE 兼容 |
| 服务端 | Linux，容器化部署（Docker Compose 单机版起步，支持横向扩展） |
| 网络 | 支持校园网内网访问；对外依赖可控（模型推理可本地化部署） |

### 2.4 约束与假设
- **约束 C1**：项目周期 12 个月，经费总额 4000 元，不得依赖付费大模型 API 长期调用（须有可离线降级方案）。
- **约束 C2**：不得存储教务系统明文密码；与教务数据交互必须为**非侵入式只读映射**（学号 `sno`、姓名 `sname`、专业成绩 `grade1`）。
- **约束 C3**：涉及真实学生数据，须符合《个人信息保护法》与学校数据管理规定，须做去标识化与最小必要采集。
- **假设 A1**：学校可提供 CAS/OAuth 2.0 统一身份认证对接支持；若无法对接，以邮箱验证 + 学号人工核验作为降级方案。
- **假设 A2**：试运行阶段可获得 ≥ 3 个学院的教学管理配合。
- **假设 A3**：云服务器（ECS）、云数据库（RDS）、对象存储可正常采购并保障 24/7 运行。

## 4. 数据需求

### 4.1 核心业务实体（逻辑模型）

| 实体 | 说明 | 关键字段 |
|---|---|---|
| `STUDENT` | 学生基础信息（与教务 `sno`/`sname` 只读映射） | sno(PK), sname, college, major, grade, auth_status, credit_score |
| `SKILL` | 标准化技能标签 | skill_id(PK), name, category_l1, category_l2, embedding_id |
| `SKILL_ONTOLOGY` | 技能图谱关系边 | id, src_skill_id, dst_skill_id, relation_type(先决/互补/同义), weight |
| `SKILL_COURSE_MAPPING` | 技能与学科专业映射 | id, skill_id, major_code, course_code, relevance |
| `USER_SKILL_PROFILE` | 用户技能画像 | id, sno, skill_id, level, source(自评/互评), updated_at |
| `EXCHANGE_RECORD` | 技能交换流水（核心表） | record_id(PK), giver_sno(FK), taker_sno(FK), give_skill_id, learn_skill_id, status, created_at, finished_at |
| `COLLAB_TASK` | 协作空间任务项 | task_id(PK), record_id(FK), title, deadline, status, evidence_url |
| `INTERACTION_LOG` | 全过程行为日志 | log_id, sno, record_id, action_type, duration, payload, created_at |
| `EVALUATION_GRADE` | 双向互评成绩 | eval_id(PK), record_id(FK), from_sno, to_sno, dim_scores(JSON), comment, hash, chain_proof, created_at |
| `CREDIT_LEDGER` | 信用值变动流水 | id, sno, delta, reason, ref_record_id, created_at |
| `BADGE` / `USER_BADGE` | 勋章定义与授予记录 | badge_id, name, condition_expr / sno, badge_id, granted_at |
| `DISPUTE` / `ARBITRATION_VOTE` | 争议与仲裁投票 | dispute_id, record_id, reason, status, verdict / dispute_id, voter_sno, vote, comment |
| `NOTIFICATION` | 通知中心 | id, sno, type, content, read_flag, created_at |

**继承既有数据（非侵入式）**：`STUDENT(sno, sname)` 基础表与 `GRADE(sno, course, grade1)` 传统成绩表保持只读引用，平台自身业务表通过 `sno` 外键做**逻辑关联**，不修改教务库结构。

### 4.2 关键数据规则
- **DR-1 索引策略**：`EXCHANGE_RECORD(giver_sno)`、`EXCHANGE_RECORD(taker_sno)`、`EVALUATION_GRADE(record_id)`、`INTERACTION_LOG(sno, created_at)` 建立复合索引；针对高频"互评读取"与"档案生成"做查询计划优化。
- **DR-2 缓存**：热点数据（标签树、首页集市 Top 列表、用户档案摘要）写入 Redis，设置合理 TTL 与缓存击穿保护。
- **DR-3 存证**：`EVALUATION_GRADE.hash = H(record_id + from_sno + to_sno + dim_scores + comment + created_at)`，写入后不可 UPDATE/DELETE，仅可追加修正记录。
- **DR-4 隐私**：手机号、学号在展示层脱敏；敏感字段落库加密；算法服务只接收向量与标签，不接收隐私原文。
- **DR-5 数据保留**：交换记录与评价永续保留；行为日志保留 24 个月；账号注销后个人信息去标识化。

### 4.3 向量库数据
| 项 | 要求 |
|---|---|
| 向量库 | Elasticsearch（dense_vector 字段） |
| 覆盖规模 | ≥ 50 个二级学科、≥ 1000 个核心技能标签（V1.0 目标） |
| 向量内容 | 技能标签语义向量 + 需求/供给文本向量 + 用户画像聚合向量 |
| 检索方式 | ANN（HNSW）近似最近邻，返回 Top-K + 相似度分值 |
| 一致性 | 标签库变更后触发增量重建，保证向量与关系库一致 |

## 5. 非功能需求

### 5.1 性能
| 编号 | 指标 | 目标值 |
|---|---|---|
| NFR-P-01 | 语义匹配接口响应时间 | P95 ≤ 300 ms（Top-20 召回） |
| NFR-P-02 | 普通页面接口响应时间 | P95 ≤ 200 ms |
| NFR-P-03 | 并发支撑（试运行规模） | ≥ 500 并发在线用户稳定运行 |
| NFR-P-04 | 压力测试 | 峰值 QPS 下错误率 < 1%，无内存泄漏（长时间稳定性测试 ≥ 24h） |
| NFR-P-05 | 档案生成批处理 | 1000 名用户的雷达图数据刷新 ≤ 5 min |

### 5.2 可靠性与可用性
- NFR-R-01：服务可用性 ≥ 99%（试运行期），关键服务无单点故障（SPOF）。
- NFR-R-02：数据库日增量备份，支持 7 日内任意时点恢复。
- NFR-R-03：AI 依赖降级：Embedding / 大模型服务不可用时，退化为关键词 + 标签 + 协同过滤匹配，核心流程不中断。

### 5.3 安全性
- NFR-S-01：身份认证采用 JWT，Token 有效期与刷新机制规范化；越权访问（IDOR）防护。
- NFR-S-02：传输层全站 HTTPS；密码/敏感字段加密存储（不可逆哈希 + 加盐）。
- NFR-S-03：接口限流与防刷：登录失败锁定、发布频控、互评频控。
- NFR-S-04：常见 Web 风险防护：SQL 注入、XSS、CSRF、文件上传类型与大小校验。
- NFR-S-05：遵循最小权限原则，管理员操作全程审计留痕。
- NFR-S-06：符合《个人信息保护法》，隐私政策与用户授权同意流程完备。

### 5.4 易用性与可访问性
- NFR-U-01：核心任务（发布需求、发起交换、完成互评）≤ 3 步可达。
- NFR-U-02：响应式适配移动端（≥ 375px），集市卡片在窄屏下可单手操作。
- NFR-U-03：关键操作有明确的空状态、加载态与错误提示，不出现静默失败。

### 5.5 可维护性与可扩展性
- NFR-M-01：模块化高内聚低耦合设计，前后端分离，接口契约先行为准。
- NFR-M-02：关键业务逻辑单元测试覆盖 ≥ 60%，接口提供标准化 API 文档（OpenAPI）。
- NFR-M-03：支持横向扩展：应用无状态化，Session/缓存外置，便于后续引入负载均衡与多节点部署。
- NFR-M-04：代码提交遵循 PR 审核 + Issue 追踪的工程化协作规范，主干保持可构建状态。

### 5.6 合规与伦理
- NFR-E-01：严禁将技能互助货币化、商业化，平台不提供任何形式的付费交易通道。
- NFR-E-02：互评与信用数据仅用于教育评价目的，不得用于商业画像。
- NFR-E-03：争议处理须保障双方陈述权，仲裁过程匿名但结果公示。

## 6. 技术架构需求

### 6.1 技术栈约定
| 层 | 选型 | 备注 |
|---|---|---|
| 前端 | Vue 3 + Vite + TypeScript；ECharts（雷达图）；组件库（Element Plus / Naive UI） | 像素艺术/体素风勋章视觉规范由前端实现 |
| 后端 | Spring Boot（Java 17）+ Spring Security + JWT；Spring AI（Tool Calling） | 单体模块化起步，接口按微服务边界划分，保留拆分能力 |
| 关系库 | MySQL 8（或 PostgreSQL） | 核心业务流水与画像 |
| 向量库 | Elasticsearch（dense_vector + HNSW） | 语义检索与知识库 |
| 缓存 | Redis | 热点数据、会话、限流计数 |
| 消息队列 | RabbitMQ / Kafka（择一） | 行为日志削峰填谷 |
| 对象存储 | 云 OSS / MinIO | 附件、报告、勋章素材 |
| 算法服务 | Python（FastAPI）承载 NLP 抽取 / Embedding / 图谱推理 | 与 Java 服务通过 REST/gRPC 交互 |
| 部署 | Docker Compose；Nginx 反向代理与负载均衡 | 单机起步，结构上支持多节点扩展 |

### 6.2 架构分层
```
┌───────────────────────────────────────────────┐
│  前端 SPA（Vue 3）                              │
│  登录迎宾 · 数字档案大屏 · 供需集市 · 协作工作台   │
└───────────────────┬───────────────────────────┘
                    │ HTTPS / REST（OpenAPI）
┌───────────────────▼───────────────────────────┐
│  Nginx 反向代理 + 负载均衡                       │
└───────────────────┬───────────────────────────┘
┌───────────────────▼───────────────────────────┐
│  Spring Boot 应用（模块化）                     │
│  鉴权 · 技能发布流转 · 交换流程 · 协作记录       │
│  互评存证 · 信用治理 · 档案生成 · 后台管理       │
└──┬──────────┬──────────┬──────────┬───────────┘
   │          │          │          │
┌──▼───┐ ┌───▼────┐ ┌───▼────┐ ┌───▼──────────┐
│MySQL │ │ Redis  │ │  MQ    │ │ 算法服务      │
│业务库 │ │ 缓存   │ │日志削峰│ │ NLP/向量/图谱 │
└──────┘ └────────┘ └────────┘ └──────┬───────┘
                                      │
                               ┌──────▼───────┐
                               │ Elasticsearch│
                               │ 向量库+图谱   │
                               └──────────────┘
```

> **关于"计算密集型模块 C++ 化"**：申报书中提及以 C++/JNI 实现矩阵运算以规避 GC 压力。本项目将其列为**预留优化项（P2）**，V1.0 先以 JVM 内向量化 + 成熟向量库承担计算，避免过早优化拖慢进度；若压测证明存在瓶颈，再按 JNI 方式下沉热点模块。

## 7. 接口需求（概要）

### 7.1 主要 REST 接口分组
| 分组 | 示例端点 | 说明 |
|---|---|---|
| 认证 | `POST /api/auth/login`、`POST /api/auth/callback`、`POST /api/auth/refresh` | CAS/OAuth 登录与 Token 刷新 |
| 技能本体 | `GET /api/skills/tree`、`POST /api/skills/parse`、`GET /api/ontology/graph` | 标签树、文本解析、图谱查询 |
| 供需集市 | `POST /api/demands`、`GET /api/demands`、`GET /api/demands/{id}` | 发布与检索需求卡片 |
| 匹配推荐 | `POST /api/match/recommend`、`POST /api/match/feedback` | 语义匹配与反馈 |
| 交换流程 | `POST /api/exchanges`、`PATCH /api/exchanges/{id}/status` | 邀约、状态流转 |
| 协作工作台 | `POST /api/workspaces/{id}/tasks`、`GET /api/workspaces/{id}/timeline` | 打卡、时间轴、附件 |
| 互评存证 | `POST /api/evaluations`、`GET /api/evaluations/{id}/verify` | 提交评价、存证校验 |
| 数字档案 | `GET /api/profile/radar`、`GET /api/profile/report/export` | 雷达图、报告导出 |
| 信用治理 | `GET /api/credit/ledger`、`POST /api/disputes`、`POST /api/arbitration/vote` | 信用流水、申诉、仲裁 |
| 开放能力 | `POST /api/open/tools/credit-score`、`/api/open/mcp/manifest` | Tool Calling 工具、能力清单 |

### 7.2 统一约定
- 响应体：`{ code, message, data, traceId }`；错误码分段（1xxx 参数 / 2xxx 权限 / 3xxx 业务 / 5xxx 系统）。
- 分页：`page`、`size`（默认 20，上限 100），返回 `total`。
- 鉴权：请求头 `Authorization: Bearer <JWT>`。
- 幂等：交换创建、评价提交、投票接口须支持幂等键（`Idempotency-Key`）。
