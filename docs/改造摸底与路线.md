# 知驿·漫游 —— 改造摸底与分阶段路线

> 本文记录一次完整的架构摸底结论与后续改造规划。
> 定位：在**不改动核心业务主流程**的前提下，补齐"需求文档已定义、代码尚未实现"的能力。
> 分支约定：改动只在个人分支 `yueyong` 上进行，通过 PR 合并到 `main`，不直接推 `main`。

---

## 一、一句话结论

项目主体功能（M1~M9 + S3 语义引擎）已经完整可用，**当前最值得做的不是"引入新框架"，
而是补上需求文档里已经写明、代码里尚未落地的 4 项能力**（缓存外置、接口限流、消息队列削峰、
MCP 式开放接口）。这些项都有 FR/NFR 编号支撑，属于"需求未闭环"而非"引入新技术"。

## 四、需求缺口（本次摸底的核心发现）

以下 4 项在 `docs/需求文档.md` 中有明确定义，代码中尚未实现。
均已核对过代码（零客户端依赖 / 零限流实现 / 接口为手写 JSON）。

| 需求编号 | 需求原文要点 | 代码现状 | 影响 |
|---|---|---|---|
| **NFR-M-03** | 支持横向扩展：应用无状态化，**Session / 缓存外置** | 缓存为进程内 `ConcurrentMapCacheManager` | 无法多实例部署；各节点缓存不一致 |
| **NFR-S-03** | **接口限流与防刷**：登录失败锁定、发布频控、互评频控 | 全项目无任何限流 | 登录可爆破、验真接口可枚举校验码 |
| **FR-M9-05** | 行为日志采集：点击流、停留时长、沟通频次**进入消息队列削峰后落盘** | 无 MQ；通知同步写库 | 通知失败会连带回滚主业务；事务被拉长 |
| **FR-M9-07 / FR-M9-08** | 开放能力接口：以标准化协议（**借鉴 MCP 思想**）开放匹配与评价能力 | `ToolApiController` 为手写 Map，非标准协议 | 无法被外部 Agent / 校内系统直接调用 |

> 注：`docs/需求文档.md` 技术选型表中"消息队列"一栏写作 RabbitMQ / Kafka（择一）。
> 若改用 RocketMQ，需同步更新该表并说明理由（延时消息能力适配"互评超时提醒"这一既有业务）。

## 五、改进项清单

按优先级排列。措辞统一为「现状 → 影响 → 改进方向」。

### P0（建议优先，均有需求支撑）

| # | 项目 | 现状 | 改进方向 |
|---|---|---|---|
| 1 | 缓存外置 | 进程内 ConcurrentMap，多实例不一致 | Redis 缓存 + 随机 TTL + 空值缓存；**用条件装配保证不装 Redis 也能启动** |
| 2 | 接口限流 | 无 | 登录失败锁定 + 关键接口频控（ZSet 滑动窗口 / Lua 原子计数） |
| 3 | 令牌撤销 | `logout` 为空实现，令牌不可撤销 | 引入失效名单或版本号；禁用账号的旧令牌需立即失效 |
| 4 | 定时任务并发 | 6 个 `@Scheduled` 无分布式锁 | 多实例部署前需加分布式锁（Redisson） |
| 5 | 性能基线 | 无压测数据，NFR-P-04 / AC-09 无交付物 | 先跑 baseline 压测并落档，后续所有"提升"以此为参照 |

### P1（建议做）

| # | 项目 | 现状 | 改进方向 |
|---|---|---|---|
| 6 | 通知异步化 | 同步写库，失败连带回滚主业务 | MQ 异步 + 消费幂等 + 失败重试 |
| 7 | 互评超时提醒 | 定时轮询扫描 | 可用延时消息替代轮询，降低无效扫描 |
| 8 | 文件存储 | 本地磁盘，多实例不共享 | 实现 `OssFileStorage`（接口已预留） |
| 9 | 技能批量导入 | 一次写入上千条标签 | 分批提交 + 导入结果明细（已有批次表可复用） |

### P2（可选增强）

| # | 项目 | 现状 | 改进方向 |
|---|---|---|---|
| 10 | 链路追踪 | traceId 已生成并写入响应头 / 响应体，但**日志 pattern 未引用 MDC**，导致拿到追踪号也无法在后端日志中检索 | 日志 pattern 增加 `%X{traceId}`（1 行配置） |
| 11 | 语义降级链 | `SemanticMatchClient` 仅有"通 / 不通"两态 | 补齐 NFR-R-03 要求的降级链并暴露当前通道 |

| 13 | MCP 标准化 | 手写工具清单 | 按标准协议暴露已有 3 个工具 |

## 六、明确**不**引入的技术及原因

这一节同等重要 —— 记录"评估后决定不做"的技术，避免后续重复讨论。

| 技术 | 评估结论 | 原因 |
|---|---|---|
| ShardingSphere 分库分表 | ❌ 不引入 | 当前 27 张表、试运行规模下数据量远未达到分片阈值；分片后跨片聚合（集市卡片按 `demand_id` 批量装配、画像按 `sno` 关联）会显著复杂化，且**回退成本极高** |
| Canal 监听 Binlog | ❌ 不引入 | 写入口高度集中（技能标签、图谱关系的写方法各一处），**写时主动失效缓存**即可满足；Canal 需额外维护 canal-server、binlog 格式与位点管理，收益不成比例 |
| Milvus / pgvector 向量库 | ❌ 不引入 | 向量规模为数百条技能标签，进程内精确检索已满足 P95 要求；引入需 4 个容器与约 2G 内存 |
| Nacos / API 网关 / OpenFeign | ❌ 不引入 | 项目为单体应用，需求未要求微服务化 |
| SSE 流式输出 | ❌ 不引入 | 平台无"模型生成"场景（成长周报为模板化拼装），流式无实际收益 |

## 七、分阶段路线与验收标准

### 阶段一（P0，约 2~3 周）

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 1 | baseline 压测并落档 `docs/压测-baseline.md` | 记录 4 个核心接口在 50/200/500 并发下的 P50/P95/P99 与错误率 |
| 2 | 缓存外置（可插拔） | 不装 Redis 时 `mvn test` 全绿；启用后目标接口 P95 相对 baseline 下降 |
| 3 | 接口限流 + 登录失败锁定 | 连续失败 N 次后账号/来源被锁定；正常流量不受影响 |
| 4 | 令牌撤销 | 登出后旧令牌立即失效；禁用账号令牌立即失效 |

### 阶段二（P1，约 2~3 周）

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 5 | 通知异步化 | 通知失败不再回滚主业务；重复消费不产生重复通知 |
| 6 | 互评提醒改延时消息 | 提醒时点与原有轮询 Job 行为一致，扫描量下降 |
| 7 | 对象存储 | 切换存储实现后业务代码零改动；多实例可共享文件 |

### 阶段三（P2，可选）

traceId 接入日志、降级链补齐、评测接入 CI、MCP 标准化。

## 八、本地环境准备（可复现）

### 1. 数据库

按顺序导入 `sql/` 下 10 个脚本（`01` 起，全部幂等）。**注意**：`01-schema.sql` 不包含
`04` 的 `dim_canonical` 列与 `06`/`07` 的 4 张表，**只跑 01 会埋下运行期报错**。

必须使用 `--default-character-set=utf8mb4`，否则 `08` / `10` 中的中文技能名会乱码。

验收：表数量 = 27；`zy_skill` ≈ 786 行；`zy_skill_ontology` ≈ 592 行；`zy_student` = 7 行；中文无乱码。

### 2. 必填环境变量

`application.yml` 共 9 个 `${...}` 占位符，其中**仅 2 个无默认值、必须提供**：

| 变量 | 说明 |
|---|---|
| `ZHIYI_DB_PASSWORD` | 数据库密码（无默认值） |
| `ZHIYI_JWT_SECRET` | ≥ 32 字节；长度不足时应用**拒绝启动** |

其余 7 个（DB_HOST / PORT / NAME / USER、STORAGE_ROOT、NLP_URL）均有默认值。

### 3. 本地凭据的存放位置

`application-local.yml` 已被 `.gitignore` 排除，是存放本地凭据的约定位置。
启用方式：IDEA 的 VM options 填 `-Dspring.profiles.active=local`。

**不要把凭据写入 `application.yml`** —— 该文件被 git 跟踪，会随分支进入 PR。

### 4. 启动

| 组件 | 命令 |
|---|---|
| 后端 | 运行 `com.nwu.zhiyi.ZhiYiApplication`（唯一启动类，靠组件扫描装配） |
| 前端 | `npm install`（仅首次）→ `npm run dev` |
| NLP（可选） | `python -m pip install fastapi uvicorn` → `python train.py` → `python serve.py` |

### 5. 已知环境差异（脚本硬编码）

仓库内脚本与文档存在原作者机器的绝对路径（`G:\DEV\...`）硬编码，在非该路径环境下需覆盖：

| 位置 | 覆盖方式 |
|---|---|
| `frontend/.npmrc` 的 `cache` | 设 `npm_config_cache` 环境变量 |
| `backend/build-env.ps1` 的 `MAVEN_HOME` | 直接使用 PATH 中的 `mvn` |
| `backend/run-server.ps1` 的 JDK 路径 | 设 `ZY_JAVA_HOME` 或传 `-JdkHome` |
| `scripts/backup.ps1` 的 mysql 路径 | 设 `ZHIYI_MYSQL_HOME` |
| `docs/交接说明.md` 全篇路径 | 替换为本机仓库路径 |
